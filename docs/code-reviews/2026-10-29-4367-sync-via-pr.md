- `tools/sync_english.py`: `auto_merge_allowed(paths, areas)` (strict
  allowlist: `<known area>/en.json`, `meta/<name>.json`) and
  `--check-paths --areas-file` (NUL-separated stdin).

## Findings / decisions to confirm

1. GITHUB_TOKEN PRs start no workflow. Required checks are produced by
   dispatching the two workflows on the bot branch (needs `actions: write`,
   wider than "contents + pull-requests"; the only way short of a PAT/App).
   Check runs from a dispatch attach to the head sha and satisfy required
   contexts of the same name; unverified live until the first run.
2. CODEOWNERS: code-owner review cannot be waived per path in a ruleset, so
   the sync-owned paths are un-owned. Weakens owner review of `legal`
   labels and `meta/source.json` (now protected by the path gate + the till
   being the only source). Owner to confirm.
3. Repo setting `allow_auto_merge` is false (checked 2026-10-29); not
   changed. Until it is on, the sync job fails at `gh pr merge` (loud, PR
   left open). Owner/Terraform item.
4. A brand-new area is refused by the gate (also needs a Weblate component):
   the job fails until a human merges it.
5. Ruleset (ut-infra, separate): required checks `unit` and `authors`,
   Weblate deploy key as bypass, strict "up to date" would stall the PR when
   Weblate pushes (not advised).
6. If main moves (Weblate) while checks run, the next hourly run force-pushes
   a fresh branch; stale `sync/english` is bot-owned so force is safe, but
   the ruleset must not protect `sync/*`.

## Unverified (cannot be proven from this repo)

(a) That a dispatched `test.yml` / `commit-attribution.yml` run satisfies the
required status context on the PR head sha. To prove on a throwaway branch
with a temporary ruleset before relying on it. If it does not, the PR sits
open (safe), never merges unchecked.

loudly while the earlier auto-merge setting (reset by GitHub on a new head)
needs re-enabling. Observe on the second real run.
